explicitly accepted both native HA boundaries; no Core interception is permitted.
The preserved v0.1.0 tag must not change. No deployment, merge, v0.2 tag or release
is authorized by the implementation approval.
Prepared 11 October 2026 against the existing Home Assistant Core 2026.10.0
development runtime. At design review the manifest was **v0.1.0**; the approved
development implementation now uses **0.2.0.dev0**, without a release tag.
The preserved baseline is Git tag `v0.1.0`, commit
`5f6769b2ea8398e2786a9db2b4cee7593917cbec`.

This proposal follows a review of `ARCHITECTURE.md`, `README.md`, `VALIDATION.md`,
the integration modules and all existing test modules. The recorded baseline is

The original design-only revision changed no production code or Git baseline;
the subsequent explicit approval authorized development on its own branch.

J'ai Lighting controls lighting. Names, membership, hierarchy, policies and
presets are user configuration. No installation names, physical entity IDs,
seasonal rules or dashboard layouts become source-code defaults.

Revision after product-owner review: absolute presets now use hierarchical
**most-specific-wins per property** instead of rejecting different parent/child
assignments. Independent relative faders and all v0.1.0 production behavior are
unchanged. This revision and both HA boundaries are approved for implementation.

## 1. Topology data model

Maintain one domain-wide primary topology shared by every group, preset and
display. Each group has at most one parent group. Each configured physical leaf
has exactly one parent group. Unconfigured HA lights remain outside this model.
A group may contain both physical leaves and other groups, at arbitrary depth.

Proposed records:

| Record | Authoritative fields |
| --- | --- |
| Group | `group_id`, `name`, `parent_group_id` or null, `power_policy`, `sibling_order` |
| Leaf | `leaf_id`, `identity`, `parent_group_id`, `sibling_order` |
| Preset | `preset_id`, `name`, ordered recipe targets |

Children are derived from parent references. Do not persist a second authoritative
child list or separate copies of direct members in config-entry options.
Ordering affects presentation only, never brightness arithmetic or precedence.
Names need not be unique; IDs must be unique.

For safe migration and incremental UI construction, allow multiple unattached
roots in the **same** topology store. These form a forest until the user attaches
them to a user-created root. This is not a second topology per dashboard. A root
containing every group gives installation-wide ON/OFF without special code.
Requiring exactly one visible root is an alternative requiring owner approval.

Allow empty groups while constructing/reorganizing the tree. They have identity
and a retained master but no controllable physical output; their light entity is
unavailable. Depth is unrestricted by product semantics; implementation must use
bounded input sizes and iterative traversal rather than Python recursion limits.

Every accepted edit replaces one validated topology snapshot and increments
`config_revision`. No edit sends physical lighting commands.

## 2. Group identity model

Retain one HA config entry for each group. Its existing `entry_id` remains both
the stable `group_id` and the virtual light's `unique_id`. Preserve the existing
entity-registry association, platform and domain; do not add a new unique-ID
prefix during migration. A new group receives a new config-entry identity.

Config entries host lifecycle and UI; the shared store in section 17 owns
topology and runtime values. Version-2 group entries contain a discriminated
reference such as `{kind: group, group_id: <entry_id>}`. Entry titles mirror the
configured group names; they are not topology keys.

Renaming, reparenting, adding members or changing a policy must preserve the
virtual entity's registry entry and registered entity ID. Suggest an entity ID
only on first creation. Respect HA entity-registry name overrides. Changing the
integration's configured name updates its original name/entry title without
silently overwriting a user registry override.

Removing a group is a separate destructive configuration action. Require the
user to resolve children, direct leaves and preset references first. A safe
deletion cannot silently orphan or discard them. Disabling/hiding the virtual
entity changes its UI availability, not physical membership. Disabling the
group's whole config entry blocks commands into that branch, including ancestor
commands, with a diagnostic; it does not delete the branch.

## 3. Physical leaf identity model

Use the HA entity-registry entry's stable `id` as the preferred identity, not its
mutable `entity_id` and not its `device_id`. A device can contain several lights.
The registry's `(domain, platform, unique_id)` tuple is useful diagnostic identity
information, but must not be used to bind automatically to a different entry.

Give each membership record an integration-local immutable `leaf_id`. Its
identity is one of:

| Kind | Stored identity | Resolution |
| --- | --- | --- |
| `registry` | `entity_registry_id` | Registry lookup yields current `light.*` entity ID |
| `entity_id_fallback` | `entity_id` | Exact state-machine ID, with an explicit rename limitation |

Registry update events refresh routing after an ordinary entity-ID rename.
Entity IDs are resolved again immediately before dispatch. A removed registry
entry becomes a missing reference. Never fall back to its previous entity ID,
because a different lamp may now own that ID. No automatic match by name, area,
device or similar unique ID. Explicit user rebinding is required.

HA lights without registry entries can remain supported through the fallback
kind, with a UI warning that renames require manual rebinding. If such an entity
later becomes registered, offer explicit conversion; do not silently merge two
memberships. Validate current resolution for aliases as well as stored identity.

A replacement is a new physical leaf with a new `leaf_id` and its own observed
baseline. Do not copy the removed device's retained brightness. A move/reparent
of the same leaf retains its identity and bounded target.

Select only the `light` domain. Continue rejecting J'ai virtual lights, known HA
aggregate lights and entities exposing aggregate membership. Public HA metadata
cannot prove that every third-party light is a physical endpoint. Document that
users must choose individual device lights; no promise is made about commands
hidden inside an opaque third-party aggregate.

## 4. Topology resolver

The pure resolver takes an immutable topology revision and a group ID. Iterative
depth-first traversal returns the complete ordered set of descendant `leaf_id`s,
their paths, and a reverse index of leaf-to-ancestor groups. Resolve identity and
capability through the adapter afterwards; missing devices remain in the result.
Unavailable leaves are not removed from configuration.

Maintain a visited-group set, an active traversal path and a leaf set. Finding a
cycle or a second path to the same leaf is a validation error. A final command
map keyed by physical identity is a second safety barrier, not a way to accept
invalid topology silently. If two leaf records resolve to the same entity,
reject/disable that invalid branch before dispatch rather than pick a winner.

Resolution must never call child virtual lights. The planner produces zero or
one physical intention per leaf; the adapter sends zero or one physical service
call for that intention. Power, brightness and optional properties are combined
in that call. A logical operation does not send separate brightness and color
calls to the same leaf. No retries are part of that operation.

Supported operation boundaries are one group action, one preset activation, or
one integration batch action. The native multi-entity HA limitation and the
recommended safe control contract are explicit in section 19.

## 5. Cycle, duplicate and single-parent prevention

Validate the whole candidate topology both when saving UI configuration and when
loading persistent data. Runtime validation protects against corrupted storage,
not only UI mistakes.

Reject unknown parents, self-parenting, group cycles, dangling references,
duplicate IDs, non-light leaves, aggregate leaves, duplicate physical identity,
and more than one parent for either a group or a leaf. Use canonical registry
identity and current entity resolution to detect duplicates.

Parent/child selection must submit one proposed edit, including any explicit
moves. Adding an already-owned leaf or child cannot silently steal it. Show its
current parent and require an explicit move choice. Reparenting removes the old
edge and adds the new edge in one store transaction. Reject reparenting a group
under any of its descendants.

Revalidate a form's `config_revision` on Save. If another user changed topology,
show a conflict and refreshed form rather than overwrite their changes. Presets
are resolved again against the candidate topology before the edit is committed.
For group reparenting, physical member moves, replacement and other scope changes,
recompute every affected preset's effective leaf properties and their source
targets. Preview affected presets and old/new effective values, including valid
changes caused by different inheritance. Reject invalid final states unless the
user repairs the recipes in the same configuration workflow/transaction. Never
accept the topology first and discover broken recipes afterwards (section 14).

## 6. Hierarchy master semantics

**Recommendation: independent relative faders, plus one shared retained target
per physical leaf.** Each group's master is an operator's last accepted position,
not an estimate of physical output. There is no product of ancestor faders,
per-leaf trim multiplier, normalization or derived average.

For a master move on group G, use `new_G / old_G` exactly once on each eligible
descendant physical light's real current brightness. Update only G's master.
Every other group's master stays unchanged, including ancestors and descendants.
Actual leaf observations then update the shared leaf memory and all affected
groups' power/diagnostics. This does not update other faders.

An illustrative sequence, in percentages before byte rounding:

| Operation | Parent master | Child master | Physical brightness |
| --- | --- | --- | --- |
| Initial state | 50 | 40 | 60 |
| Parent to 75: factor 1.5 | 75 | 40 | 90 |
| Child to 20: factor 0.5 | 75 | 20 | 45 |
| Parent to 50: factor 2/3 | 50 | 20 | 30 |
| Manually change physical light | 50 | 20 | 80 |
| Child to 40: factor 2, clipped | 50 | 40 | 100 |

The child still displaying 40 after an ancestor move means “my fader is at 40,”
not “my descendants are at 40%.” Explain this in UI help and action descriptions.
The ordinary HA brightness attribute represents the master; separate metadata
may describe physical output, never replace the master with an aggregate.

Presets, FULL power, manual leaf changes and topology edits do not reset any
master. After any absolute command, the next relative move still uses the real
physical state and the addressed group's previous master. A same-position master
request remains a no-op, even after an absolute command. There is no hidden
“reapply fader” behavior. Changing these rules requires owner approval.

## 7. Off-state hierarchy semantics

Group power is ON if any available descendant reports ON. It is OFF when at
least one descendant is available and all available descendants report OFF.
Unavailable descendants have unknown power, even when the group appears OFF.
The group light is unavailable if there are no available descendants.

If the addressed group has an available ON descendant, use the active v0.1 path:
scale only available ON dimmable leaves with real brightness. Individually OFF
leaves and their retained targets remain unchanged. This applies even if an
entire child branch is OFF. An active ancestor does not move that OFF branch's
memory merely because the child is included in resolution.

If the group appears OFF, move only its own master and scale the shared bounded
brightness targets of its resolved dimmable descendants once. Available OFF
leaves without memory bootstrap from a valid OFF brightness attribute, otherwise
255. Unavailable leaves with existing memory can have their targets scaled;
their unknown physical state is never treated as a confirmed OFF observation.
Do not bootstrap unknown devices from invented capability/state.

An OFF ancestor therefore changes the targets a child will later RESTORE, but
does not move the child's fader. A subsequent OFF child move scales the same
targets again using the child's independent factor. There are no second copies
of child restore targets to synchronize.

Example: parent/child masters 100/100, shared target 200; parent to 50 makes
target approximately 100 and leaves child master 100. Child to 50 makes target
approximately 50 and leaves parent master 50. Child RESTORE then uses 50.
Sequential clipping happens at every step; 200 -> clipped 255 -> half is about
128, never 200 recovered from hidden excess.

For a wholly unavailable but nonempty subtree, allow the explicit
`jai_lighting.set_master` action to move the retained master and scale existing
cached targets with **no dispatch**. Report that physical power is unknown.
This preserves v0.1's useful unavailable-memory behavior. Standard light actions
remain subject to HA availability handling. Empty groups can retain a fader
through the explicit action but have no targets. No action is queued for reconnect.

Any later real ON observation supersedes that leaf's retained brightness. Stale
OFF attributes do not overwrite a pending scaled target. ON does not replay
missed operations automatically when an unavailable device reconnects.

## 8. Power policy model

Policies are a per-group enum, initially `RESTORE` and `FULL`. Existing groups
migrate to `RESTORE`; propose `RESTORE` as the new-group default. A policy applies
only to a bare group ON, never to OFF, master-only actions or presets.

| Request | Planned behavior |
| --- | --- |
| Bare ON, RESTORE | Turn every available OFF descendant on at its retained level; already-ON leaves keep their real levels |
| Bare ON, FULL | Turn every available descendant on; dimmable leaves receive 255, including already-ON leaves |
| OFF | Observe real ON brightness, then turn every available descendant off; retain all masters/targets |
| `set_master` | Relative move with current power preserved; do not invoke the group's ON policy |

RESTORE includes previously individually switched-OFF leaves, as v0.1 does.
Binary leaves receive power without brightness. Repeated OFF preserves memory.
Successful FULL observations replace retained levels with real reported results,
including device quantization. Unavailable devices retain their existing targets.
FULL does not save an invented successful 255 baseline for a failed device.

**Explicit brightness on `light.turn_on` overrides the bare-ON policy.** Perform
v0.1's relative master movement and RESTORE power-on as one plan, even for a FULL
group. Calculate final outputs before dispatch, not by issuing two operations.
While active, scale ON leaves and restore OFF leaves unchanged; while OFF, scale
retained targets before restoring them. Brightness zero follows native HA OFF
semantics and leaves the master unchanged.

Propose that explicit CT/color/effect ON requests also use RESTORE power-on plus
the explicit compatible fields; FULL is reserved for bare ON. Otherwise changing
a color could unexpectedly force every dimmer to 100%. This precedence is an
owner decision. OFF has no optional property assignments.

Presets are absolute plans and bypass all group policies. An absolute preset
power-ON with brightness omitted does not inherit RESTORE or FULL brightness.
It requests power and the recipe's fields only, leaving the device's own retained
brightness behavior in effect.

## 9. Capability aggregation model

Discover capabilities from HA registry capabilities and current light state:
`supported_color_modes`, supported-feature flags, temperature bounds and
`effect_list`. Use HA brightness/color mode helpers in the adapter. Capability
declarations are not configuration fields entered by a user.

Cache last-known capability facts for unavailable devices, marked stale. Cache
enables stable controls during temporary outages; it does not establish current
availability or authorize dispatch to a missing/disabled entity. Refresh on
state/registry changes and membership edits. Unknown new devices do not invent
capabilities. Compute aggregation from the complete resolved subtree.

| Group control | Advertised when | Application |
| --- | --- | --- |
| Power | Every nonempty group has a light entity | Available controllable leaves |
| Brightness | At least one descendant supports dimming | Eligible dimmable leaves only |
| CT | At least one descendant supports native CT with valid bounds | Native CT leaves only, per-leaf clamp |
| Color | At least one descendant supports HS/RGB/XY/RGBW/RGBWW | Color-capable leaves only |
| Effects | At least one descendant advertises EFFECT and a usable effect name | Leaves advertising the requested name |

Master state/action exists even for a binary-only group, but its normal light
entity advertises `ColorMode.ONOFF` and cannot offer a useful brightness slider.
Mixed dimmable/binary groups expose dimming; binary members ignore brightness.

Produce a legal HA `supported_color_modes` set, not a raw union: use canonical
`HS` for color, add `COLOR_TEMP` if native CT exists; otherwise `BRIGHTNESS` for
dimming-only groups or `ONOFF` for binary-only groups. Do not include BRIGHTNESS
or ONOFF alongside richer modes. Do not advertise WHITE, FLASH or TRANSITION in
v0.2. RGBW/RGBWW leaves participate through canonical color conversion.

The virtual `color_mode` is the group's selected supported control axis, not a
claim that every descendant is in that mode. Initialize deterministically to HS,
then CT, then BRIGHTNESS/ONOFF as applicable; change it on compatible explicit
requests. Report color/CT scalar state only when available ON compatible leaves
agree after conversion within documented comparison tolerances (1 K CT, 1 degree
hue with circular comparison, 1 percentage point saturation). Otherwise omit
that scalar and expose mixed/unknown status. Do not invent an average or use a
last request as proof of actual color. Effect state is similarly unknown/mixed
unless compatible ON leaves agree. These virtual-state semantics need HA runtime
tests and owner approval; native light UI has no universal mixed-color display.

HA's light service may convert unsupported color inputs before calling a virtual
entity. Consequently, an externally supplied CT on an RGB-only virtual group may
arrive as color. The integration cannot reconstruct the discarded input reliably.
Its native controls advertise only valid capabilities. Presets and the domain
control action preserve the original property kind and enforce strict skip
semantics. This HA boundary must be documented, not hidden by guessing intent.

## 10. Brightness semantics and property preservation

Retain v0.1's numerical rules: master stored as integer 3..255; explicit master
percentage accepts finite 1..100 and converts with half-up rounding/minimum 3.
Leaf brightness targets are integer 1..255. Ratios use stored bytes. No zero
master, unbounded intermediate memory or unclipped target is persisted.

For active relative moves:

`target = clamp(floor(real_brightness * new_master / old_master + 0.5), 1, 255)`

Missing/invalid real brightness on an ON dimmable leaf means skip that leaf for
relative movement. Do not substitute memory or infer 100%. Same output can be
omitted. Binary leaves do not receive brightness.

The requested sequence remains intentional, approximately at byte resolution:

| Master | First leaf | Second leaf |
| --- | --- | --- |
| 50 | 100 | 60 |
| 60 | 100 | 72 |
| 30 | 50 | 36 |
| 90 | 100 | 100 |
| 50 | 55.6 | 55.6 |

Brightness commands include no CT, color or effect fields. Do not apply HA light
profiles/default recipes intentionally or synthesize color fields. HA or a
physical integration may apply its own configured defaults/device constraints;
verify actual state and diagnose unexpected changes. J'ai cannot transact or
override hidden device firmware behavior.

Absolute preset brightness is distinct: convert a finite percentage in (0,100]
to a bounded byte with minimum 1, then assign it without multiplying any fader.
Zero is rejected in the recipe brightness field; use explicit power OFF. A 1-byte
leaf target can be represented even though a master cannot be below 3 bytes.

## 11. Color-temperature semantics

Use integer Kelvin. Native CT support means `COLOR_TEMP`, not a color light that
could approximate white. Do not translate CT to RGB on incompatible leaves in a
preset/domain action. Skip those leaves for CT while applying other valid fields.

Propose group slider bounds as the envelope of valid native descendant ranges:
minimum of minima, maximum of maxima. Clamp each leaf to its own advertised
range and report clamped leaf IDs/requested/applied values. Thus a requested
2700 K reaches a capable 2700 K leaf unchanged; a leaf whose minimum is 3000 K
receives 3000 K; a brightness-only leaf receives no CT assignment. Invalid or
missing bounds make CT ineligible for that leaf until discovered.

This envelope keeps mixed devices useful, including disjoint ranges, but can
produce mixed actual CT. A common-intersection slider or strict out-of-range
rejection are alternatives for owner approval. Do not silently claim all leaves
reached the requested temperature.

A CT-only recipe/request omits brightness. Do not reset brightness, color/effect
or power unless explicitly requested or necessarily changed by the device's mode
switch. A CT assignment necessarily selects the device's CT mode; keeping its
previous active RGB mode simultaneously is impossible.

## 12. Color and effect semantics

A recipe color is one tagged value: HS, RGB or XY; never several simultaneous
representations. Validate finite ranges (HS 0..360/0..100, RGB integer 0..255,
valid XY chromaticity). Reject black RGB and invalid black/undefined chromaticity
as power substitutes; use power OFF. Normalize nonblack RGB chromaticity to full
channel magnitude for conversion so its incidental intensity does not act as an
undocumented second brightness control. Preserve its hue/saturation, not a
separate RGB intensity setting.

On each compatible leaf prefer its requested input mode if supported; otherwise
convert deterministically through HA color utilities to the first supported mode
in the order HS, RGB, XY, RGBW, RGBWW. Persist the tagged input, not every converted
form. RGBW/RGBWW conversion uses HA utilities and leaf temperature bounds where
needed; missing required bounds skip that conversion with a reason. Conversions
can be approximate and device gamut can differ. No per-device calibration or
white-channel editing is promised in v0.2.

The planner must select a native leaf field itself. Do not rely on HA's broader
CT-to-RGB or RGB-to-CT fallback when that would turn an unsupported property into
a different one. Native CT-only and brightness-only leaves ignore color.
Canonical HS on the virtual entity lets HA normalize ordinary color requests;
presets/domain actions retain their original tagged form for deterministic planning.

Color-only commands omit brightness. The conversion must not intentionally
rescale it. Mode switches, RGBW channel extraction and hardware limitations can
alter perceived output; the planner guarantees omitted brightness, not identical
luminous flux. Real post-command brightness remains the next fader baseline.

Effect names are the case-sensitive names HA reports. Advertise a sorted union
and apply an effect only where that exact name is supported. Do not invent an
alias or a generic stop-effect string; use a leaf's advertised stop/off option.
Reject a final effective leaf intention assigning effect together with CT or
color in v0.2, because device precedence is not reliably portable. For presets,
perform this check after per-property inheritance, not on target rows before
resolution. Brightness plus effect is allowed
when the leaf supports both, with actual reporting/failure diagnostics. Selecting
a static color can necessarily stop an effect even though no explicit effect
field was sent; document the device's mutually exclusive modes.

## 13. Preset data model

Presets are named, persistent **absolute** recipes with immutable IDs. Each
target uses `{kind: group, id: group_id}` or `{kind: leaf, id: leaf_id}` plus a
sparse property object:

`power?: on|off; brightness_pct?: number; color_temp_kelvin?: integer;`
`color?: tagged value; effect?: string`

At a target, an absent property means **no local assignment**: inherit the nearest
applicable ancestor assignment, if any. Only a property absent from the entire
applicable path means leave the physical leaf unchanged. Null is invalid rather
than an inheritance-cancellation marker. An empty property object is invalid;
omit that target instead. Presets do not contain master assignments, policy
overrides, transitions, scripts or non-light devices.

Targets may intentionally overlap along the single-parent hierarchy. Parent
assignments establish defaults; deeper child assignments override only the
properties they explicitly contain. A physical leaf target is the most specific
possible assignment. Omitting power or CT on a child brightness row does not
erase inherited power or CT. Target row order is presentation only.

A group target resolves dynamically using the current topology. Replacing a lamp
inside that group automatically makes its successor part of that recipe, with
capabilities rediscovered. A recipe targeting a specific leaf intentionally
targets that device: removing/replacing it requires editing that recipe reference.
The UI must show this exception before deleting a directly targeted leaf.

Power-preserving sparse behavior applies to the **final inherited property set**,
not to each row separately:

| Recipe intention | Available leaf behavior |
| --- | --- |
| Effective OFF only | Capture real ON brightness and send OFF |
| Effective ON plus optional fields | Send ON plus compatible absolute fields; do not apply group policy |
| No power assignment on the path, leaf ON | Apply compatible fields through a single `light.turn_on` call; leave power ON |
| No power assignment on the path, leaf OFF | Skip light properties with reason `off_power_preserved`; do not power on or stage a hidden recipe |

Reject effective OFF plus brightness/CT/color/effect on the same final leaf,
including combinations inherited from different targets. A descendant ON can
override ancestor OFF; validate the resulting power rather than reject the mere
presence of an overridden OFF assignment.
Applying optional properties to an OFF device through HA `light.turn_on` would
turn it on; v0.2 should require explicit power ON when that is intended. This
proposal deliberately does not introduce deferred color/effect state. This
OFF/property-only behavior is retained under the architecture's approval in
principle; the inheritance revision does not change it.

Successful real ON brightness updates the shared retained target. **No group
master position changes**, including groups named in recipe targets. Reactivating
an absolute preset resolves the current topology and reapplies its effective
absolute assignments; it is not a relative operation. The next master movement
uses the group's existing master position and each leaf's real resulting physical
state. Preserve fields with no effective assignment, subject to unavoidable
mode/device constraints described above.

## 14. Preset resolution, inheritance and conflict model

**Product-owner decision: most-specific-wins independently per property.** This
rule applies only to absolute preset resolution. It does not change relative
faders, power policies or the non-preset domain batch conflict rules in section 19.

### Resolution pipeline

1. Validate recipe field types/ranges and references against one topology revision.
   Canonicalize target identity and check duplicate assignments to the same
   target/property. Differing same-specificity assignments are invalid, even if
   a deeper target would later shadow them; identical duplicates collapse.
2. Resolve each group target to its complete physical leaves. For each physical
   leaf and each property independently, collect assignments from targets on its
   single topology path. Include an explicit target of that physical leaf.
3. Select the deepest applicable target **that assigns that property**. A physical
   leaf outranks every ancestor group. Depth is measured in the current primary
   topology, not recipe order. A deeper target omitting a property has no effect
   on its inherited value. Assemble one effective sparse property set per leaf.
4. Validate that final effective property set for semantic/mode conflicts, before
   considering availability or capability. Keep the winning source target for
   every property and the leaf's topology path for errors and previews.
5. Apply current availability/capability filtering and leaf-native conversion to
   those already-selected properties. A skipped winning assignment does not fall
   back to a less-specific ancestor assignment. Capability does not change rank.
6. Build one combined physical intention per leaf and dispatch each leaf at most
   once. A globally invalid recipe dispatches nothing.

Because every group and leaf has one parent, applicable group targets on a leaf
form an ancestor chain. Siblings have disjoint physical leaf sets and cannot
conflict with one another. Two distinct groups at the same depth cannot both
apply to a leaf in a valid topology; if that occurs, reject the topology rather
than invent row precedence. There is no “last row wins.”

For same-target duplicates, compare canonical authored property values before
brightness byte rounding or device-native color conversion. Numerically equal
values such as 30 and 30.0 are identical; different percentages remain conflicting
even if both would round to the same brightness byte. Kelvin/power/effect values
and tagged color values must likewise agree. Distinct tagged color formats at
the same target/property are conflicting unless the stored tag/value is identical;
do not infer approximate perceptual equality. Two rows for the same target can
assign disjoint properties. Their row order never affects the result.

### Inheritance examples

The following symbolic labels describe user-configured nodes, not built-in names
or entity IDs. The tree is `R -> A -> A1 -> physical leaf`, with sibling `B` and
another direct branch `C` under R. Preset assignments are:

| Target | Local assignments |
| --- | --- |
| R | Power ON, brightness 30%, CT 2700 K |
| A | Brightness 50% |
| A1 | CT 2200 K |
| B | Brightness 80% |
| One physical leaf under A1 | Brightness 90% |

The effective values before capability filtering are:

| Leaf location | Power and source | Brightness and source | CT and source |
| --- | --- | --- | --- |
| C | ON from R | 30% from R | 2700 K from R |
| A, outside A1 | ON from R | 50% from A | 2700 K from R |
| A1, without explicit leaf override | ON from R | 50% from A | 2200 K from A1 |
| Explicitly targeted leaf under A1 | ON from R | 90% from the leaf | 2200 K from A1 |
| B | ON from R | 80% from B | 2700 K from R |

Likewise, parent brightness 100% and child brightness 30% is valid: child leaves
receive 30%, other parent descendants receive 100%. Child brightness does not
replace the whole parent's property object. A parent OFF with descendant ON and
brightness is valid where ON wins; parent OFF with descendant brightness and no
power override is an invalid effective OFF-plus-brightness state.

### Final-state conflicts and provenance

After inheritance, reject effective OFF plus any brightness/CT/color/effect,
simultaneous color and CT, and effect together with color/CT under v0.2's existing
compatibility rules. Overrides of one property do not silently erase another.
For example, ancestor CT plus descendant color remains a conflict; different
property names cannot cancel each other. Null/omission cannot clear inherited CT.
The user must revise the recipe targets/defaults so the final state is valid.

Each validation error identifies the physical leaf (stable ID/current entity ID
where resolvable), its path, the final effective properties, and the source
target/row for each conflicting property. Report even if the device is offline
or would not support one of those fields. Do not let capability filtering conceal
an invalid recipe or change its precedence.

Run this pipeline at recipe Save, topology Save and activation. Preset meaning is
topology-relative: reparenting a group or moving a physical member can introduce,
remove or change inherited assignments without changing recipe rows. Recompute
all affected effective states and show affected presets, old/new values and
source targets in the topology-edit preview. Valid changed meaning can be saved
after review; invalid effective states block the edit unless repaired in the same
configuration workflow/transaction. Missing target references block activation
until repaired; ordinary unavailable leaves under valid targets are runtime skips.

## 15. Preset Home Assistant representation

**Recommend one integration-provided `scene` entity per preset.** Override
`Scene.async_activate` to call this integration's resolver/planner; do not pass
virtual groups recursively into HA state reproduction. The native scene offers
dashboard activation, automation/script `scene.turn_on`, and Developer Tools
Actions. Its activation timestamp means attempted activation, not proof of full
success or a permanently active recipe.

| Representation | Assessment |
| --- | --- |
| Scene | Native model for a lighting recipe; stable entity identity, one-shot activation |
| Button | Also usable for one-shot actions, but duplicates a scene without additional semantics |
| Domain action | Useful for strict field intent and detailed results; complements scene activation |
| Select | Implies a persistent current selection that manual/relative changes make misleading |
| Script | Good external orchestration, but recipe ownership/editing and lighting planning belong here |

Use a separate config entry of `kind: preset` per preset, with `preset_id` equal
to its entry ID and its scene's `unique_id` equal to that ID. This avoids tying
scene lifecycle to an arbitrary group that may later be deleted. It adds a native
integration entry per preset; that UI tradeoff remains the design choice approved
in principle, rather than a new decision introduced by inheritance.

Propose `jai_lighting.activate_preset` with a native scene selector, optional HA
service response containing structured results, and the same planner as the scene.
Scene activation raises a descriptive HA action error on failed leaves after
attempting valid leaves. Domain activation can return per-leaf results when
response data is requested, with an explicit `partial`/`failed` status; without
response data it raises on failures. Neither interface hides partial failures.
Do not expose a second button or a fictitious “currently active preset” select.

Integration-provided recipes are edited in the integration's flows, not assumed
to be editable by HA's built-in scene editor. No YAML, text JSON editor or custom
dashboard is required.

## 16. Configuration and UI flow

Use HA Config Flow/Options Flow with native selectors, translated labels/help and
validation messages. Continue using the pinned runtime's `probatio` schema API
and framework-supplied `OptionsFlow.config_entry`.

Add integration presents **Add group** / **Add preset**. Add group proceeds:

1. Enter name and choose a parent group, or no parent.
2. Select direct physical lights and existing child groups.
3. Show current ownership and request explicit moves for already-owned members.
4. Choose RESTORE/FULL and optional sibling order.
5. Preview resulting hierarchy/capabilities and Save one validated transaction.

Create further subgroups through Add group with the desired parent selected.
Configuring an existing group offers rename, membership, parent, policy and
ordering edits. Existing missing/disabled members remain visible and removable.
Replacing a lamp removes the old membership and adds the new selected physical
light in the same Save. Group entity IDs, master and group-targeted automations,
dashboards and recipes remain valid. Moving ownership never sends lighting calls.

Preset editing is a multi-step native flow: name; add/edit/remove target rows;
group or physical selector; choose which properties are locally assigned; property
selectors; inheritance/effective-state/conflict preview; Save. Omitting a local
field means “inherit; otherwise leave unchanged.” Power offers
ON/OFF/inherit-or-unchanged. Do not label omission as an unconditional “leave
unchanged” when an ancestor assigns that property. Display capability coverage
and OFF/property-only behavior. Do not require users to declare modes or copy
parent fields into every child.

For each property show, where practical, local assignment/override, inherited
value, effective value and source group/leaf. A child brightness override of 50%
can show inherited ON and 2700 K from its parent without storing duplicate fields.
If descendants differ, show a mixed summary with an expandable per-leaf preview;
do not invent a single effective scalar. Show authored effective values separately
from capability skips, range clamps and device-native conversion. Reordering rows
does not change any effective value.

Group selections use stable IDs with current names/paths as labels. Duplicate
names show paths/short IDs. Physical entity selectors are converted to registry
identities at Save. Preset physical selections are restricted to configured
leaves. Reparent/replace/member-move previews must include affected presets and
their recomputed effective values/source targets, not only a reference count.

Removing nonempty groups or directly targeted leaves requires a separate flow
that specifies moves and recipe repairs before deletion. HA config-entry deletion
can bypass Options Flow; its remove hook must preserve affected records as
orphaned/blocked and create a Repair issue instead of silently dropping topology.
No hardware operation or accidental broadening of preset scope occurs.

## 17. Persistence schemas and ownership

Use one HA-managed `homeassistant.helpers.storage.Store` for the authoritative
domain snapshot. No external database, runtime dependency or user YAML file.
Store version 2 and payload `schema_version: 2` are distinct from the eventual
integration release version. Store ownership avoids competing per-group restore
arrays and permits atomic topology/preset edits.

Illustrative shape; placeholders denote generated identities, not configuration
defaults or valid literal UUIDs:

```json
{
  "schema_version": 2,
  "config_revision": 1,
  "state_revision": 1,
  "groups": {
    "<group-entry-id>": {
      "name": "<user-chosen-name>",
      "parent_group_id": null,
      "power_policy": "RESTORE",
      "sibling_order": 0
    }
  },
  "leaves": {
    "<leaf-id>": {
      "identity": {
        "kind": "registry",
        "entity_registry_id": "<registry-entry-id>"
      },
      "parent_group_id": "<group-entry-id>",
      "sibling_order": 0
    }
  },
  "presets": {
    "<preset-entry-id>": {
      "name": "<user-chosen-name>",
      "targets": [
        {
          "target": {"kind": "group", "id": "<group-entry-id>"},
          "properties": {"power": "on", "brightness_pct": 30}
        }
      ]
    }
  },
  "runtime": {
    "group_masters": {"<group-entry-id>": 255},
    "leaf_brightness_targets": {"<leaf-id>": 128}
  }
}
```

An optional versioned capability-cache section contains only discovered mode,
range and effect facts with freshness metadata; no invented live power state.
Do not persist calculated descendants, ancestor indices, derived group power,
unbounded targets or requested-but-unconfirmed ON brightness as actual memory.
Store sparse authored preset rows only; effective per-leaf inherited properties
and source maps are transient plans/previews. Never flatten inherited defaults
into duplicate child assignments on Save. Payload schema version 2 defines the
most-specific-per-property rule; future semantic changes need explicit versioning
and migration, not an implicit change to existing recipe meaning.
Diagnostics are bounded runtime records; no unbounded command/event history.

Before accepting a topology edit or master/off-target transition, serialize and
await `Store.async_save` on the complete candidate snapshot, then publish it.
A failed pre-dispatch save rejects the operation without commands or changing
the published master. For active commands, persist the accepted master and
existing/observed retained targets before dispatch; do not save desired physical
output as confirmed observation. Successful observations replace target memory.
External observations may use coalesced delayed saves; flush before the next
operation and on graceful shutdown. Abrupt power loss can lose unsaved recent
observations; report this limit rather than promise hardware transactions.

The domain manager serializes every store write. State listeners update the live
observation cache and acknowledgement signals immediately, then schedule memory
reconciliation/persistence through that manager. They must not replace a saved
snapshot with a stale delayed copy or wait for the operation lock before signalling
acknowledgement. Reconcile observations received during an awaited save/dispatch
before publishing the final runtime snapshot; keep the newest real observations.

If a post-dispatch observation save fails, expose storage failure and the fact
that devices may already have changed. Keep live state authoritative in memory;
block new configuration/relative operations until a fresh snapshot saves safely.
Never roll devices back as a storage workaround. Startup reads and validates
storage, resolves registry references, then reconciles actual ON observations
without dispatching any lighting commands. Unsupported future schemas must fail
setup without overwriting the file; invalid topology likewise requires repair.

HA config entries and this store are separate files, not a cross-file atomic
database. Use a small persisted configuration transaction journal with operation
ID, before/candidate references, host-entry intent and phase for add/remove/migrate.
Prepare the store, create/update/remove host entries using HA APIs, then finalize
the published revision. Recovery reconciles a recorded incomplete transaction
idempotently before serving controls. Never expose a half-created branch.
Prototype and failure-test this protocol before enabling migration. Do not claim
`async_save` also makes HA config-entry writes atomic.

## 18. Migration from v0.1

Perform installation-wide preflight before converting any group, since v0.1
allows direct overlap and v0.2 requires single ownership. Take a HA backup first;
retain byte-preserving legacy entry/restore snapshots and a migration journal.
The Git tag recovers source, not the installation's HA data.

1. Read all v0.1 entries and their effective data/options. Retain entry IDs,
   registry associations, names, ordered membership and validated master/targets.
2. Map each existing flat group to a parentless v0.2 group with RESTORE policy.
   Do not invent a root or reparent by name. Preserve identity as section 2 says.
3. Convert existing entity-ID membership to registry IDs where an exact registry
   entry currently exists. Keep missing/unregistered members as explicit fallback
   references with diagnostics. If an old ID was already renamed before migration,
   require explicit rebinding; metadata cannot safely reconstruct its old identity.
4. Detect shared physical membership across all legacy groups. Stop conversion
   and request ownership choices; never silently deduplicate, select a parent,
   copy a lamp into two branches or infer hierarchy. A guided migration/Repair
   flow must let the owner select primary ownership and review affected groups.
5. Read version-1 ExtraStoredData (`master`, entity-ID-keyed `memory`). For an
   unambiguous leaf, convert its bounded target to the new leaf ID. For former
   overlaps, the owner's chosen owning group's memory wins; preview differences
   before approval. Preserve all group masters. Missing/corrupt restore values
   use bounded v0.1 defaults with diagnostics; never overwrite the legacy backup.
6. Validate the entire candidate version-2 store and all registry associations.
   Stage/save it and the recovery journal before changing HA config entries.
7. Through `async_migrate_entry`, update entries to config-entry version 2 while
   preserving `entry_id`. Coordinate globally, rather than let whichever entry
   loads first decide ownership. Finalize only when every required entry matches
   the validated migration transaction.
8. Load physical observations. Actual ON brightness wins over migrated targets;
   OFF/unavailable leaves keep migrated targets. Migration/startup sends no calls.

On preflight/validation/storage failure, leave v0.1 entry/restore data intact and
report the blocking issue. If conversion is interrupted after some entry updates,
block inconsistent v0.2 setup and resume or restore from the recorded transaction;
do not replace data with defaults or operate a partly migrated installation.
Keep conversion deterministic and restartable. Do not run v0.1 and v0.2 planners
concurrently against the same leaves during this transition.

Safe downgrade requires restoring the pre-migration HA backup/legacy entry and
restore snapshots **and** the source from tag `v0.1.0`. Replacing code alone leaves
version-2 config entries that v0.1 cannot read. Later v0.2 edits cannot generally
be flattened back without losing hierarchy/presets. Do not promise an automatic
lossless downgrade. Preserve the backup until the owner accepts the deployment.

## 19. Concurrency and native service boundaries

One domain operation lock serializes plans, dispatch/acknowledgement and topology
transactions. Use a coherent immutable topology revision plus freshly sampled
physical states for each operation. Pending configuration forms do not hold locks.
Event listeners update observations/acknowledgement signals without taking the
operation lock; otherwise an operation waiting for an event would deadlock.

Within the lock: validate request/revision; resolve leaves; snapshot observations
and capabilities; plan; save accepted state; dispatch independent leaf commands
with bounded parallelism; collect every result; reconcile real observations;
save/publish diagnostics; release. Capture each leaf's routing identity in the
plan and recheck it before dispatch, especially after registry events. Carry the
originating HA context into physical calls. No recursive lock acquisitions or
virtual child service calls. Cancellation must release listeners/locks and mark
uncertain dispatched leaves; never automatically retry on cancellation.

A preset/batch uses one operation ID and one command map across all targets.
Propose a domain `jai_lighting.control` action for explicit power/property batches
and strict original-property semantics; its selectors accept J'ai groups and
configured physical leaves. This non-preset batch keeps its explicit-assignment
merge rules: identical/disjoint assignments combine; different assignments to the
same leaf/property reject the batch, without hierarchy overrides or row ordering.
Final mode-conflict checks still precede capability filtering. Preset inheritance
is not extended to this live batch interface by the product-owner change. Keep
its sparse brightness fields absolute, exactly like recipe assignments; relative
master movement belongs to `set_master` or the group's normal brightness control.
The domain action does not apply group power policies. Keep
`jai_lighting.set_master` as a domain batch handler using HA target resolution,
not separate entity callbacks: reject ancestor/descendant pairs in one relative
request, because independent old masters yield competing factors. Disjoint
groups are allowed. One group with all descendants is the normal master target.

**Native HA multi-target limit:** `light.turn_on`/`turn_off` invoke each virtual
entity independently. A request targeting both parent and child can therefore
create two operations and touch a physical leaf twice, despite each planner
deduplicating correctly. Configuring an automation to target both does not become
a deduplicated batch automatically. Do not group calls by HA context ID: a context
can span multiple actions and is not a unique service invocation identifier.

Recommend a documented supported contract: native light actions target one
virtual group per call, or multiple disjoint groups; overlapping multi-target
actions use the integration batch/preset interface or their common ancestor.
No core service interception or patches. This is an explicit product acceptance
boundary: the one-command-per-leaf guarantee holds for each supported logical
operation, not arbitrary external collections of separate virtual entity calls.
If the owner requires the guarantee across an overlapping native multi-target
service invocation, implementation must wait for a verified HA batching API or
a different exposed control model; this proposal does not claim that solved.

External physical controls/independent automations do not share this lock. A
device can change after the snapshot or during dispatch. Next operations use the
latest real observation. No distributed atomicity, synchronized hardware timing
or automatic rollback is claimed. Serialize J'ai operations, bound service waits,
and expose uncertainty rather than assume a timeout proves no device change.

## 20. Failure and acknowledgement model

Use the existing 10-second physical service timeout and 2-second state-report
wait initially, without advertising transitions. Waits per concurrently dispatched
leaf are bounded. No retry, reconnect replay or compensation commands.

| Condition | Result |
| --- | --- |
| Some leaves unavailable/disabled | Skip them, attempt valid available leaves, report IDs/reasons and coverage |
| All leaves unavailable | Power/property/preset operation has no eligible dispatch and reports an HA action error; explicit retained-master action follows section 7 |
| Empty subtree | Power/property activation reports no eligible leaves; topology remains editable |
| Registry reference missing/device removed | Keep configuration, report missing identity; never route to a same-name replacement |
| Unsupported optional field | Skip that field, apply other valid fields; no whole-group error solely for incompatibility |
| No leaf supports any requested field | Report a clear no-applicable-property error instead of a misleading success |
| Service exception or timeout | Mark that leaf failed/uncertain, attempt other leaves, report partial failure |
| Preset same-specificity conflict, invalid inherited final state or dangling target | Reject before any dispatch; report leaf, effective properties and source targets |
| Partial preset device failure | Preserve successful results, return/raise partial failure; no scene-wide rollback |
| Storage failure | Follow section 17; distinguish pre-dispatch rejection from post-dispatch uncertainty |

An explicit compatible power assignment still counts as applicable when optional
fields are skipped. Property-only OFF skips remain visible and an all-skipped
operation reports no applicable output. An unavailable skip alone does not make
an otherwise successful partial-coverage operation throw; failed attempted
commands do. Scene timestamps cannot establish success.

Retain the addressed master once a valid plan is accepted/persisted, including
partial command failure. Do not revert it and cause successful leaves to rescale
on a repeat request. Do not write desired failed brightness as actual memory.
Same-master reissue stays a no-op; recovery uses a new deliberate action/preset
or physical control, not hidden replay.

Observe before dispatch and subscribe before sending to avoid missed fast
reports. For power, match reported power. For brightness, accept exact target or
a valid changed ON brightness as a device-reported, possibly quantized result,
as v0.1 does; record exact versus changed-report acknowledgement separately.
This is not proof that an external change was caused by this command.

CT/color/effect require a matching report of each commanded optional property,
using the comparison tolerances in section 9 and converted leaf-native color.
If a device quantizes beyond tolerance, report unconfirmed application rather
than silently accept any changed color as success. Matching pre-existing fields
need no new report. Device-specific tolerance/calibration is a future extension;
hardware testing must confirm defaults. Late reports remain authoritative.

Expose last operation ID/status, attempted/succeeded/skipped/failed/unconfirmed
counts, skipped-property reasons, unavailable/missing leaves, per-leaf timeout
stage and temperature clamps. Bound detail size and make full sanitized detail
available via integration diagnostics. No credentials, config paths or unrelated
HA entity state should appear in diagnostics.

## 21. Dashboard-facing metadata

All displays read/control the same group and scene entities. Frontend root-view
preferences are not engine configuration. Seasonal branches stay present year
round; dashboards decide visibility and HA automations decide seasonal behavior.

Expose a versioned metadata contract, with current entity IDs resolved from stable
identities:

| Attribute | Meaning |
| --- | --- |
| `jai_group`, `jai_metadata_version`, `group_id` | Discovery marker/schema/stable group identity |
| `parent_group_id`, `parent_entity_id` | Primary parent or null |
| `child_group_ids`, `child_entity_ids` | Direct child groups in sibling order |
| `direct_leaf_ids`, `direct_member_entity_ids` | Direct physical memberships, with missing resolution explicit |
| `entity_id` | Complete resolved physical member entity IDs for HA group conventions/aggregate rejection |
| `descendant_leaf_count`, `depth`, `sibling_order` | Tree structure, without card/layout information |
| `power_policy`, `master_brightness`, `master_brightness_pct` | Configuration and independent retained master |
| `capability_coverage`, `color_state_status`, `ct_state_status` | Eligible/total counts and uniform/mixed/unknown values |
| `config_revision`, `last_operation_status` | Discovery consistency and bounded outcome summary |

Preset scenes expose stable preset ID, referenced target IDs and recipe revision,
not a misleading active-state flag. A read-only `jai_lighting.get_topology` action
with service response can return the full versioned topology/capability snapshot
for reusable frontend templates without large repeated state attributes.
Implementing a frontend that consumes it is out of scope. Native dashboards may
still need manual card selection; this is metadata, not promised auto-generation.

Preserve normal HA authentication/permissions. Metadata supplies no custom
display-specific backend copies, authorization bypass or dashboard navigation
state. Group/leaf IDs are identity references, not secret capabilities.

### Required preset inheritance tests

These are test specifications for the later approved implementation, not tests
added to production/test code by this design revision. Use abstract configured
nodes and physical fake lights; do not encode installation names or entity IDs.

1. **Parent default + child brightness:** parent 30%, child 50%; child leaves get
   50%, other parent descendants keep 30%, each through at most one command.
2. **Other properties survive override:** parent ON/30%/2700 K, child brightness
   50%; final child leaves receive ON/50%/2700 K with correct per-property sources.
3. **Multi-level inheritance:** parent ON/30%/2700 K, child brightness 50%, deeper
   child CT 2200 K; its leaves receive ON/50%/2200 K.
4. **Physical leaf override:** parent brightness 30%, child 50%, one leaf 80%; that
   leaf gets 80%, its siblings get 50%, and inherited power/CT remain intact.
5. **Sibling overrides:** two sibling branches override independently to 50% and
   80%; neither affects the other's leaves or unoverridden branches.
6. **Identical duplicate assignment:** repeated identical target/property values
   collapse without duplicate commands; disjoint fields on duplicate target rows
   combine without losing inheritance.
7. **Same-specificity conflict:** two different values for one target/property
   reject the whole recipe before dispatch. Reverse rows and include a deeper
   shadowing target: the invalid duplicate remains invalid, never “last row wins.”
8. **Inherited OFF plus descendant brightness:** effective OFF with inherited/
   overridden brightness is invalid. Error includes the leaf, final properties and
   their source targets. A companion case with descendant ON demonstrates that
   overriding power before final validation can make the final state valid.
9. **Inherited CT plus descendant color:** retain both assignments through
   resolution, then reject their final mode conflict. Do not silently drop CT,
   including when capability filtering would otherwise skip it. Cover inherited
   effect plus incompatible descendant color/CT similarly.
10. **Group reparent:** moving a group under a different preset-targeted ancestor
    changes inherited effective values/sources; topology preview lists affected
    presets and old/new results. Invalid new effective states block Save unless
    repaired in the same workflow/transaction.
11. **Physical member move:** moving one leaf between primary groups changes its
    inherited recipe results without moving any fader. Preview valid changes and
    reject invalid changes; its explicit leaf overrides remain most specific.
12. **Capability filtering after inheritance:** pick winning assignments first,
    validate final semantics next, then skip unsupported fields. A binary leaf
    inherits effective ON/brightness/CT but receives ON only. A winning unsupported
    effect does not fall back to a less-specific supported ancestor effect. Mode
    conflicts remain errors even on incompatible/unavailable leaves.
13. **Preset leaves all masters untouched:** capture every group master before
    activating a multi-level preset and assert the complete master map is unchanged
    after success or partial device failure.
14. **Relative movement after preset:** old group master 50%, preset makes real
    leaf brightness 80%; moving the master to 25% scales the real 80% by 25/50 to
    approximately 40%, with byte rounding. It does not reuse pre-preset memory,
    reset the master or derive a master from the preset brightness.

Repeat valid inheritance cases with reordered target rows and assert identical
effective values, provenance and physical command plans. Add absent/no-ancestor
property cases that preserve existing fields and confirm null cannot cancel
inheritance. Exercise the same resolver through native scene and domain preset
activation; keep non-preset absolute batch and relative-master rules unchanged.

Pure model tests use deterministic snapshots and plans. Adapter tests use real
pinned HA setup, registries, native service handling and controlled fake devices,
extending the existing fixtures rather than touching installation hardware.
Fresh-instance disk tests verify migration/persistence. Use fake time/events for
timeouts and delayed/quantized reports. Test storage/config-entry interruption
with fault injection, not only successful conversion.

Before any release, run the existing validation commands against the approved
implementation: `.venv/bin/python -X faulthandler -m pytest -q`,
`.venv/bin/ruff check .`, `.venv/bin/ruff format --check .`. Then validate a small
real mixed-capability installation for reporting tolerances, native HA controls,
FULL/RESTORE, OFF movement and preset partial failure. Do not infer hardware
correctness from fake devices or bypass the design approval gate.

### Module reuse and redesign

No existing production module can remain wholly unchanged while delivering this
design. Reuse tested primitives and HA lifecycle patterns; replace flat ownership
and per-group mutable leaf memory explicitly.

| Existing file | Proposed treatment after approval |
| --- | --- |
| `engine.py` | Redesign flat `FaderEngine` around pure node state/shared leaf state and operation plans; retain half-up clamp, ratio, bounded memory and observation rules |
| `coordinator.py` | Redesign into domain manager plus group views; reuse context propagation, service wait/listener cleanup and failure collection patterns |
| `membership.py` | Redesign identity resolution/validation; retain light-domain and known aggregate rejection checks |

implementation organization, not new product features or external dependencies.

## 23. Explicit v0.2 non-goals

- Building automation, heating, climate, sensors, media or unrelated switches.
- User-specific installation topology, names, entity IDs or built-in preset names.
- Seasonal topology creation/deletion or per-display group copies.
- Custom dashboards/cards, dashboard generation, display navigation or layout.
- DAGs, physical multi-parent membership, recursive virtual-light dispatch.
- Derived-average masters, multiplied ancestor trims or hidden unclipped output.
- Transitions, fades, flashing, synchronized hardware timing or device calibration.
- Generic script execution inside recipes, scheduling or sensor-trigger engines.
- Automatic retries, reconnect replay, transactional device rollback or automatic
  registry rebinding to a replacement lamp.
- Public publication, GitHub Release, deployment, new Git commits/tags, or version
  changes as part of this design task.

Ordinary HA automations/scripts can combine lighting scenes with unrelated
devices and sensor conditions. J'ai stores only lighting topology and recipes.

templates can use the same topology/identity contract. Secondary views should
reference existing groups, never assign a physical leaf another primary parent.
Persist no prospective trim factors or season/dashboard fields “for later.”

## PRODUCT OWNER DECISIONS REQUIRED

The architecture is approved **in principle**. The register below records the
retained design choices and the explicit preset-inheritance decision; it does not
ask the owner to repeat approval of each unchanged recommendation. Final review
of this revision is still required, and implementation remains unauthorized.
The remaining boundary confirmations are listed after the register.

1. **Independent faders:** only the addressed group's master moves. Ancestor,
   child and manual/absolute operations never synchronize other faders. A master
   displays a position, not average/effective descendant output (section 6).
2. **Shared leaf memory:** one bounded brightness target per physical leaf; OFF
   ancestor/child moves act on that same target. Active ancestors leave OFF child
   targets untouched. No stored ancestor-factor products (sections 6–7).
3. **Topology roots and empty groups:** allow several roots while building/migrating
   one domain topology, with an optional user-created common root; allow empty
   unavailable groups. Alternatively require a single explicit root (section 1).
4. **Ownership edits:** require explicit moves for already-owned lights/groups;
   never silently steal membership. Block/recover deletions with unresolved
   children, leaves or preset references (sections 5, 16).
5. **FULL and faders:** bare FULL sets dimmable descendants to 255 but preserves
   every master. A subsequent relative movement uses the old fader position and
   real new output; same-master reissue stays a no-op (sections 6, 8).
6. **ON precedence/defaults:** default to RESTORE. Explicit brightness uses relative
   movement plus RESTORE, overriding FULL; explicit color/CT/effect also overrides
   bare FULL to avoid an unintended 100% reset (section 8).
7. **Unavailable master movement:** allow the explicit master action to adjust
   cached targets even with no available leaves, without assuming physical OFF
   or replaying on reconnect. Native light availability remains HA-controlled
   (section 7).
8. **Identity/replacement:** prefer registry IDs; allow clearly marked entity-ID
   fallbacks; never auto-rebind removed identities. New replacement lamps start
   from their own state. Direct-device presets require explicit reference repair,
   while group-targeted controls survive replacement (sections 3, 13, 16).
9. **Disabled branch behavior:** disabling a config entry blocks ancestor commands
   through that branch; merely hiding/disabling its virtual light entity does not
   remove membership or stop parent control (section 2).
10. **Mixed-capability presentation:** union-based useful controls, compatible-only
    application, canonical HS/CT virtual modes, omitted scalar color/CT when mixed,
    and no ordinary brightness slider for a binary-only group (section 9).
11. **Temperature bounds:** use the group range envelope and per-leaf clamping with
    visible diagnostics, retaining the proposed choice over intersection-only or
    strict rejection (section 11).
12. **Color/effects:** use tagged HS/RGB/XY, normalized RGB chromaticity, deterministic
    HA conversions including RGBW/RGBWW, exact effect names, no CT approximation
    on RGB-only leaves in strict actions, and no effect+color/CT combination
    (section 12).
13. **Sparse preset power:** omission inherits an ancestor assignment if present;
    absence from the entire path leaves that property unchanged. With no effective
    power assignment, property-only recipes leave OFF devices OFF and skip their
    properties rather than stage a deferred recipe. Effective OFF plus properties
    is invalid; effective ON with no brightness bypasses group restore/FULL and
    uses device-native retention (section 13).
14. **Preset inheritance — explicitly decided by the owner:** deepest applicable
    target wins independently for each property, with physical leaf most specific.
    Child brightness keeps inherited power/CT. Siblings remain disjoint. Identical
    duplicates collapse; different same-target/property assignments at the same
    specificity reject without row-order precedence. Resolve inheritance, validate
    final mode/power conflicts with per-property source targets, then filter by
    capability. Recompute/preview affected presets on topology edits and reject
    invalid states unless repaired in the same workflow (sections 5, 13–14, 16).
15. **Preset UI:** native scene entities plus one config entry per preset, edited
    in integration flows; no select or duplicate button. Retain the extra entry
    count rather than introduce an installation-level host/subentry design in this
    revision (sections 15–16).
16. **Control interfaces and one-command guarantee:** native light calls use one
    group or disjoint groups. Overlapping targets require the common ancestor,
    preset or domain batch. Relative batches reject ancestor/child targets. If
    arbitrary overlapping native multi-target calls must also deduplicate as one
    invocation, that is an unresolved requirement blocking this control design
    (section 19).
17. **HA color-input boundary:** native services may convert unsupported input
    before J'ai receives it. Strict property-kind skipping is guaranteed by
    presets/domain actions, while native controls follow their advertised modes
    and HA preprocessing; this boundary is explicitly accepted (section 9).
18. **Partial results:** unavailable/unsupported skips permit other valid leaves;
    attempted command failures produce partial failure; all-skipped output errors;
    no rollback/retries. Accepted masters persist after failed dispatch. Scene
    timestamps signify attempted activation only (sections 15, 20).
19. **Acknowledgement:** retain v0.1 changed-brightness quantization acceptance,
    distinguish it from exact matches; require CT/color/effect matching within the
    proposed tolerances and report unconfirmed application outside them. No causal
    guarantee against external races (sections 9, 19–20).
20. **Storage/lifecycle:** retain shared HA Store authority with per-group/preset
    lifecycle entries, pre-dispatch accepted-state saves, coalesced external
    observation persistence and a tested recovery journal for cross-file updates.
    Storage failure blocks unsafe further mutations (section 17).
21. **Migration conflicts and rollback:** retain guided primary-owner selection
    for legacy overlaps, selected owner's memory with preview, parentless flat
    migration and no automatic root. Require retained legacy data/HA backup;
    source tag alone is insufficient for data downgrade (section 18).
22. **Metadata/scope:** retain the versioned discovery contract and optional
    read-only topology action, without building a dashboard or seasonal/non-light
    automation engine. Require pinned-runtime tests and small hardware validation
    before release (sections 21–24).
